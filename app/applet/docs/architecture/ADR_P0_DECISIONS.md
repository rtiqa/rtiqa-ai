## ADR-001: Local Database Source of Truth

### 1. Context
يحتوي المشروع حالياً على قاعدتي بيانات منشأتين وتعملان بالتوازي:
- `app.RtiqaDatabase` (الإصدار 1، 4 جداول، تغذي مباشرة شاشات تصفح الكورسات والملف الشخصي في الواجهة).
- `core.RtiqaDatabase` (الإصدار 8، 32 جدولاً، تغذي مشغل الدروس، إدارة المدارس، والمزامنة عبر `AppDiContainer`).
هذا الانقسام يتسبب في تشتت حالة التطبيق وازدواجية الذاكرة وغياب مصدر حقيقة موحد.

### 2. Decision
الاتجاه المعتمد رسمياً: **اعتماد `core.RtiqaDatabase` كمصدر الحقيقة المحلي المستهدف (Target Source of Truth) لكافة بيانات التطبيق مستقبلاً.**

### 3. Why
لأن معمارية المشروع العامة مبنية على تعدد الموديولات المؤسسية (`core-domain`, `core-data`, `core-database`)، وتحتوي `core.RtiqaDatabase` بالفعل على النطاق الشامل للجداول المؤسسية والتعليمية المتوافقة مع طبقة النطاق (Domain Layer). هذا القرار هو توجيه استراتيجي للمستقبل ولا يعني أن `app.RtiqaDatabase` كانت تعتبر مجرد مسودة سابقة دون دور؛ بل كان لكل منهما استهلاك فعلي في التطبيق.

### 4. Alternatives Considered
- **اعتماد `app.RtiqaDatabase`:** تم استبعاده لأنه يقتضي هدم وإعادة بناء 28 جدولاً وعزل موديولات الـ core.
- **الإبقاء على القاعدتين مع وسيط تزامن محلي:** تم استبعاده لتفادي التعقيد العالي جداً وخطر تضارب البيانات المستمر.

### 5. Consequences
- سيتطلب التطبيق لاحقاً ترقية هيكل جدول `user_profiles` في `core` ليستوعب الحقول الخاصة بالواجهة الموجودة في `app`.
- سيعاد توجيه الـ ViewModels في موديول `:app` للاستهلاك عبر الـ UseCases لاحقاً.

### 6. Migration / Implementation Notes
- **ممنوع حذف `app.RtiqaDatabase` في هذه المرحلة.**
- يجب أن تبقى `app.RtiqaDatabase` تعمل بشكل طبيعي حتى يتم:
  1. كتابة كود التحويل والمطابقة (Mapping/Migration) لبيانات `UserProfile` بين الجدولين (`user_profile` و `user_profiles`).
  2. التحقق من التكافؤ الوظيفي الكامل لجميع الشاشات وتأكيد خلو أي مراجع برمجية لـ `app.RtiqaDatabase`.
  3. إجراء اختبارات تراجع دقيقة قبل إيقافها نهائياً.

### 7. What is explicitly NOT being done yet
- لا يتم حذف أي كلاس أو جدول متعلق بقاعدة `app.RtiqaDatabase`.
- لا يتم تعديل أي Room Schema أو تنفيذ أي Migration برمجياً الآن.
- لا يتم تغيير أي كود في `CourseViewModel` أو `MainViewModel` الآن.

## ADR-002: Backend Authority

### 1. Context
يحتوي المستودع على خادم Ktor تمهيدي داخل المجلد `deploy/ktor-starter` يدعم حالياً مسار `/api/v1/auth/login` ومسار `/me`، بينما تتوقع واجهات شبكة أندرويد 5 مسارات إضافية غير منفذة بعد (التسجيل، الكورسات، الدروس، البروفايل، المزامنة).

### 2. Decision
الاتجاه المعتمد رسمياً: **اعتماد `deploy/ktor-starter` ليكون هو الـ Backend الرسمي المستهدف للمشروع.**

### 3. Why
لتوحيد التقنيات عبر بيئة لغة Kotlin بين العميل والخادم، والاستفادة من البنية التحتية المهيأة مسبقاً (Supabase Auth و PostgreSQL و Netty Engine)، مع الحفاظ على خفة وسرعة معالجة خادم Ktor.

### 4. Alternatives Considered
- **اعتماد نظام BaaS خارجي فقط أو خادم Node.js مستقل:** تم استبعاده لتركيز الجهد البرمجي وتوحيد المنظومة داخل هذا المستودع.

### 5. Consequences
- يتطلب الالتزام بتطوير واستكمال الـ Endpoints الناقصة في خادم Ktor وصيانتها كجزء من بنية النظام الشاملة.
- توحيد عقود الشبكة بين أندرويد و Ktor لمنع أي فجوات تواصل مستقبلية.

### 6. Migration / Implementation Notes
- يجب أولاً تثبيت وتوثيق عقد الشبكة الموحد (API Contract) ونماذج البيانات (DTOs / Server Data Model).
- يتم تنفيذ الـ Endpoints الناقصة بالتتابع وفقاً للأولويات المعتمدة (بدءاً بـ `register` ثم المحتوى ثم المزامنة).

### 7. What is explicitly NOT being done yet
- لا يتم بناء أو برمجة أي مسار جديد في Ktor في هذه الخطوة.
- لا يتم تعديل عقود Retrofit الحالية في أندرويد.
- لا يتم تشغيل أو تغيير إعدادات خادم Ktor الآن.

## ADR-003: Offline Conflict Resolution Strategy

### 1. Context
يدعم تطبيق أندرويد العمل بدون اتصال بالإنترنت عبر طوابير المزامنة (`sync_queue`) ومسيرات العمل في الخلفية (`WorkManager`). عند إعادة الاتصال ورفع التغييرات قد تتعارض البيانات المعدلة أوفلاين مع الحالة المركزية على الخادم.

### 2. Decision
الاتجاه المعتمد مبدئياً: **اعتماد استراتيجية المزامنة ذات المرجعية المركزية للخادم مع التحكم بالتزامن المتفائل وإدارة النسخ (Server-authoritative synchronization with versioning / optimistic concurrency control).**

### 3. Why
لحماية نزاهة البيانات المركزية (Data Integrity)، ومنع الكتابة فوق بيانات أحدث تمت عبر مشرفين أو معلمين، مع تجنب الاعتماد الحصري والخطير على ساعة هاتف العميل (Clock Drift).

### 4. Alternatives Considered
- **Client Wins:** مرفوض تماماً لخطره الشديد على نزاهة البيانات في سياق المؤسسات والتعليم.
- **Last Write Wins (بناءً على توقيت الهاتف فقط):** غير كافٍ بذاته لعدم دقة ساعات الأجهزة.
- **Server Wins البحت بدون إدارة نسخ:** تم تجنبه لأنه يؤدي لفقدان غير مبرر لجهد الطالب المنجز أوفلاين.

### 5. Consequences
- سيتطلب النظام إضافة حقول النسخ (Version Numbers / Entity Tags) في الكيانات الحساسة على الخادم وقاعدة البيانات المحلية.
- سيتطلب بناء معالج في الخادم لفحص النسخة السابقة قبل تطبيق التحديث، وإرجاع حالة تعارض واضحة إن وُجدت.

### 6. Migration / Implementation Notes
- لا تعتمد السياسة على ساعة جهاز العميل وحدها إطلاقاً.
- لا تفترض السياسة أن جميع الجداول تحتاج نفس الاستراتيجية المعقدة؛ فالبيانات الإضافية (مثل تسجيل إكمال درس) قد تتبع استراتيجية دمج تراكمية (Additive / Idempotent)، بينما الدرجات وتحديث الملف الشخصي تتبع Versioning.
- يجب جرد وتحديد الكيانات التي تحتاج Versioning بدقة قبل كتابة كود المزامنة.

### 7. What is explicitly NOT being done yet
- لا يتم تعديل أي جدول لإضافة حقول النسخ أو التوقيت حالياً.
- لا يتم بناء أي منطق لحل التعارض في العميل أو الخادم في هذه الخطوة.

## 8. ADR-004: Gemini AI Integration Architecture

### 1. Context
يحتوي المشروع محلياً على كلاس `GeminiAiRepositoryImpl` وجدول `ai_insights`، وتوجد متطلبات لتفعيل ميزات المساعد الذكي والتوصيات التعليمية.

### 2. Decision
الاتجاه المعتمد رسمياً: **اعتماد معمارية الاتصال الوسيط عبر الخادم: (Android → Backend/Ktor → Gemini API).**

### 3. Why
1. **الأمان وحماية الاعتمادات:** منع تسريب مفتاح الـ API الخاص بـ Gemini داخل ملف الـ APK أو كود العميل.
2. **التحكم بالحصص والتكلفة:** ضبط معدلات الاستهلاك لكل مستخدم ومنع استنزاف الميزانية (Rate Limiting & User Quotas).
3. **المرونة والمراقبة:** إمكانية تعديل تعليمات النظام (System Instructions) ونماذج الذكاء الاصطناعي على الخادم فورياً ومراقبة جودة الردود مركزياً دون الحاجة لتحديث تطبيق أندرويد في المتجر.

### 4. Alternatives Considered
- **الاتصال المباشر من أندرويد (Android → Gemini Direct):** تم استبعاده نهائياً لمخاطره الأمنية والمالية الفادحة وصعوبة حماية مفاتيح الـ API المضمنة في التطبيق.

### 5. Consequences
- سيتطلب بناء مسار مخصص في Ktor لاستقبال أسئلة التطبيق وتمريرها لخوادم Gemini باستخدام الـ SDK المناسب للباك إند.
- تخزين الـ API Key حصراً في متغيرات بيئة الخادم السحابي (`.env` / Environment Variables).
- لا يعتبر كلاس `GeminiAiRepositoryImpl` الحالي تكاملاً حقيقياً ومكتملاً مع Gemini حتى يتم ربطه بالمسار الفعلي وإثبات عمله تشغيلياً.

### 6. Migration / Implementation Notes
- يجب الحفاظ على جدول `ai_insights` المحلي كطبقة تخزين مؤقت للنتائج والتحليلات التي يسترجعها العميل من الخادم.
- يتم إعداد العقد الشبكي بين أندرويد وخادم Ktor لخدمات الذكاء الاصطناعي لاحقاً.

### 7. What is explicitly NOT being done yet
- لا يتم تضمين أي مفتاح API لـ Gemini داخل كود أندرويد.
- لا يتم بناء الـ Endpoint الوسيط في Ktor في هذه الخطوة.
- لا يتم تعديل `GeminiAiRepositoryImpl` أو إطلاق أي استدعاءات شبكية الآن.
